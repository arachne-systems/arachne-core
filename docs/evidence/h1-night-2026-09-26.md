# H1: Fork recovery evidence

## BLUF

The runtime can stage a switch to a verified winning membership step, carry signed revocations onto it, recover retained own data, retry a lost local action once, and settle retained epochs from authenticated reports. It saves branch records with the workspace candidate. It changes authority and deletes snapshots only after adoption. H1 is in progress. The full convergence suite and bounds audit remain.

### Wire and storage

- `DFBQ` version 1 and `DFBP` version 1 carry at most 256 branch rows. A row is a search hint. The receiver fetches and verifies the step, then computes its class and digest locally.
- `DFMH` version 2 carries the epoch fingerprint, head fork key and an MLS signature. Version 1 is rejected.
- `runtime/branch/meta` names the retained snapshot epochs and the orphan flag. `runtime/branch/snapshot/<u64 BE>` stores each sealed snapshot. The store transaction includes the exact staged branch candidate.
- `DFBS` version 1 seals only MLS provider and member records. The active record store retains common history once. Restore verifies that the attached common history reaches the exact snapshot state.
- The snapshot limit and the total rollback limit remain bounded. A size limit can shorten the rollback window. It does not reject a valid membership commit. Other snapshot errors fail the commit.
- The runtime reports `branch_switch_staged`, `membership_branch_kept`, or `orphaned` as branch results. An orphan cannot publish or create a membership change. It needs administrator re-add.

### Shared-file hooks for H2

`persistence.rs` calls `membership::fork::prepare_candidate` before save, includes `fork::records`, accepts the branch prefix, and calls `fork::restore` before publishing restored authority. H2 owns the storage API migration. H1 owns the fork data and adoption hooks.

### Behavior and bounds

- `DFRO` version 1 encodes a signed order and its anchor proof. `DFGO` version 1 carries the encoded order on membership gossip. A relay provides no authority.
- A switch rebases each valid losing revocation onto the winning chain. A winning node also carries a verified losing Remove when it still has the common snapshot.
- `runtime/branch/order/<digest>` stores each order in the candidate transaction. There are at most 64 orders. Each encoded order must fit `MAX_WIRE_STEP` (117 KiB).
- A valid Remove or Leave keeps new protected publications blocked until its target is absent or the order becomes invalid. Membership reception stays enabled. Adoption advances order proofs with the accepted chain. Applied, expired or invalid orders are removed. The runtime logs the discard reason. A failed carried commit also returns `carried_revocation_discarded` and its reason.
- Membership activity wakes the host when a carried order can be committed. A node does not attempt to commit its own removal. It sends the order so another member can commit it.
- The runtime still requires the whole committed step to fit one control reply. A large checkpoint or long anchor proof can exceed this bound. Paged proof transport remains a known gap. The runtime rejects such a commit.
- The integration branch adds protected stream APIs after this lane's base. They must use the same transmission gate before new encryption, including existing producers. Root has this integration requirement.

## Snapshot byte bound

H2 measured a 3,117,170-byte MLS provider value at 2,049 members. The old per-snapshot limit rejected it, even though the total rollback budget is 16 MiB. A 4 MiB retention fixture failed with `invalid branch snapshot size`.

Each snapshot may now use up to 16 MiB. The total remains 16 MiB and the count remains 64. The native store splits large logical values into bounded physical records. A 4 MiB fixture keeps exactly four epochs and deletes older snapshots. Security branch checks: 22 passed. Actual large-roster snapshot retention is a joint H2 capacity check; it is not proved by the size fixture alone.

### Behavior

- Signed heads and authenticated `membership_current` replies provide observations. A fingerprint must match local accepted state at that exact epoch before the report counts.
- Epoch E settles when every member in its saved roster reports E+1 or later on that chain. A local adoption supplies this node's report. Removed members do not provide new reports, so those epochs can remain until a retention bound applies.
- The driver stages `branch_settlement_staged` through the same store transaction as other branch changes. Reports are volatile. Restart can delay settlement; it cannot create a false report.
- A small in-memory cache holds public rosters and fingerprints from retained snapshots. It avoids opening the same MLS snapshot for each report. The cache follows the retained epoch set and is empty after restart.
- Candidate copies share immutable sealed snapshot bytes. Staging a publication does not copy the 16 MiB rollback budget before save. Snapshot deletion releases the shared value after the old candidate is gone.

## Step 10 checkpoint: Received data from a losing branch

The delivery regression first failed with `foreign plaintext must identify its losing branch`. It now passes and checks the flag after snapshot restore.

Pending plaintext stays in the inbox after a switch. Each object above the common fork epoch gets a durable `from_losing_branch` flag. The Client and JSON pending-object views expose the flag and the authenticated author epoch. Re-publication uses only this node's retained authored data. It does not use foreign pending plaintext.

The inner inbox cache format is `DFIC` version 6. Old version 5 records are rejected. Objects already accepted and removed from the Core inbox are outside this flag update; the host owns that application storage.

### Records and host results

- `runtime/branch/actions` uses `DFAC` version 1. It stores at most 64 locally issued non-revocation actions with their exact encoded step and retry state. A received action is never added to this ledger.
- A valid lost management action is prepared again on the winner. An invalid action, a second loss, or an issued invitation link returns `action_lost`. An issued link pins the discarded checkpoint; the host must issue a new link. Restoring only its public invitation control would not repair that link.
- `runtime/branch/republications` uses `DFRP` version 1. It retains at most 4,096 objects and 512 KiB of encoded data. A full queue drops the oldest data and reports `republication_lost`; it cannot block membership repair. These bounds cover retained data, not an application archive.
- The driver preserves `branch_state`, `fork_epoch`, `first_unsettled`, `action_id`, `reason`, `carried_revocation`, `republication`, `republication_lost`, and `publication_id` in its committed JSON result.
- Action and retention outcomes are returned by the drive call. They are not a separate acknowledged notification inbox.
