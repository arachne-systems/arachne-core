## Capacity and limits

The measured security export at 2,049 members has 2,082 records and about
151,164,109 bytes (144.2 MiB) of value data. The largest logical provider
value is 3,116,923 bytes.
The runtime stores it in 512 KiB parts. This retained admission data is a
persistent storage cost; it is not a Cargo cache.

The complete encoded join history is 1,223,560 bytes against the 2 MiB limit.
This count includes authorization bytes. At that roster, a single Add step
is 820 bytes and a batch of 128 Adds is 76,389 bytes. These are history codec
measurements, not a claim that 2,049 live peers joined over Iroh.

A separate attempt to register another invitation on the un-updated large
roster exceeds the management commit bound. The storage test reuses its
existing invitation and reads the public checkpoint. Member self-updates
reduce later management commit size. This report does not claim that the
management limit was removed.

The measured rollback snapshot is 3,208,876 bytes. The native commit saves
its pre-admission epoch 17 in seven physical snapshot parts. Restore reads
those parts and preserves the snapshot. The 16 MiB budget can hold about five
snapshots of this size; this runtime test retained one pre-admission epoch.
The capacity check passed in 8.68 seconds.

H1 limits each snapshot and the complete rollback window to 16 MiB. It also
limits the window to 64 epochs. Size pressure drops old snapshots. It must
not block a normal membership commit. A verified losing branch outside the
retained window becomes orphaned.
